# rotom 会话复盘第三轮：error 与 aborted 停点来源

## A. 重跑停点统计

固定窗口仍为 2026-10-31 至 2026-11-07。更新后的脚本识别到 554 次 handoff、38 次 aborted，并在本地生成 99 个只读样本。总量和第二轮一致。

### A.1 错误类别

`prevErrorCategory` 的全量分布如下。`n/a` 表示前一条 assistant 消息不是 error 或 aborted；`abort_other` 表示 aborted 的通用模板。

| 类别 | 全部 handoff | `bare_continue` |
|---|---:|---:|
| `n/a` | 459 | 18 |
| `abort_other` | 38 | 22 |
| `other` | 28 | 26 |

| `timeout` | 2 | 2 |
| `connection` | 2 | 1 |
| `rate_limit` | 2 | 0 |
| `stream_terminated` | 1 | 1 |
| `overloaded` | 1 | 0 |
| **合计** | **554** | **74** |

只看 57 个 error 停点，类别为：`other` 28、`fetch_failed` 12、`bad_request` 5、`auth` 4、`timeout` 2、`connection` 2、`rate_limit` 2、`stream_terminated` 1、`overloaded` 1。

34 个 error 后只回复“继续”的停点中，`other` 有 26 个。它们的本地错误模板主要是目录刷新失败、流失败和上游错误帧；另外有 3 个明确的 bad request、2 个响应头超时、1 个流终止、1 个连接超时和 1 个无附加原因的 fetch failure。仓库只记录类别和汇总，不记录错误正文。

### A.2 连续 error 尝试次数

| 连续尝试分桶 | 全部 handoff | `bare_continue` |
|---|---:|---:|
| `n/a` | 497 | 40 |
| `<=1` | 30 | 22 |
| `<=2` | 2 | 0 |
| `<=4` | 21 | 9 |
| `<=8` | 2 | 2 |
| `>8` | 2 | 1 |
| **合计** | **554** | **74** |

没有 `<=3` 样本，因此 `<=4` 的 21 个实际都是连续 4 次 error。由此得到：

- 57 个 error 停点中，25 个连续失败至少 4 次，即常规 3 次重试已经耗尽，占 43.9%；30 个只有 1 次 error，占 52.6%；另有 2 个连续失败 2 次。
- 34 个 error 后只回复“继续”的停点中，12 个连续失败至少 4 次，占 35.3%；22 个只有 1 次 error，占 64.7%。
- 22 个单次即停的 `bare_continue` 样本里，有 3 个明确属于 bad request 或无效工具参数。其余是目录刷新失败、流失败或不透明的请求失败。单次即停不能统一解释成“全部不可重试”，但也不能在没有错误合同映射时统一自动续跑。

**结论：** 第一轮把 34 个 error + “继续”全部称为“可重试且已耗尽”过宽。当前能由尝试次数直接证明重试预算已耗尽的是其中 12 个。全量 error 停点中则有 25 个达到至少 4 次连续失败。已知的 bad request 和鉴权错误不应进入自动续跑；其他单次即停类别需要先按 provider 合同明确是否可重试。

**结论：** 当前证据没有证明 compaction 或扩展是主要来源。12 个“aborted 后继续”样本中，5 个更像跨进程或跨会话恢复，7 个仍无法判断。不能把 22 个 `bare_continue` + aborted 全部算作“本应在原运行内自动续跑”，也不能把它们全部当作用户主动按停。

## C. toolUse 停点

全量有 17 个 toolUse 停点：`bare_continue` 5、`other` 11、纠正关键词 1。本地样本文件包含全部 5 个 `bare_continue`，本轮逐一读取。

| label | 判断 | 证据摘要 |
|---|---|---|
| `e6ee8bdbd6` | 进程或会话结束，具体原因未知 | 工具调用后没有结果；约 39 分钟后出现新的启动标记和“继续”。 |
| `2378dc9fd0` | 进程或会话结束，具体原因未知 | 工具调用后没有结果；约 15 分钟后出现新的启动标记。 |
| `83bdaa7ff0` | 进程或会话结束，具体原因未知 | 工具调用后没有结果；约 39 分钟后出现新的启动标记。 |
| `c685c1dc4f` | 工具长时间运行 | 工具结果在约 8 分 44 秒后、用户再次发言时才落盘，随后 assistant 被中断。 |
| `a6ed18f0de` | 工具长时间运行 | 工具结果在约 2 小时 42 分后、用户再次发言时才落盘，随后 assistant 被中断。 |

Jev 的辅助分类同样得到 3 个“进程或会话结束”和 2 个“工具长时间运行”，但 5 个判断的置信度都低于 0.7。最终分类依据仍是工具结果是否出现、时间间隔和启动条目。

**结论：** 5 个样本中，3 个能证明会话在拿到工具结果前结束，但不能区分进程崩溃和用户关闭终端；2 个是长时间运行的工具调用。没有样本能证明 assistant 正常拿到工具结果后主动选择不收尾。对 toolUse 停点，不应盲目重放工具；恢复时应先查原工具是否仍在运行、是否已有结果，以及写操作结果是否 unknown。

## 对 REPORT.md P1 范围的影响

1. **P1 应继续只覆盖明确可重试且预算已耗尽的 error，不应按 stop reason 粗粒度覆盖全部 error。** 本周能直接证明至少 4 次连续失败的有 25 个，其中 12 个后续只回复“继续”。`auth`、`bad_request` 和无效工具参数不应续跑。单次即停的流失败、目录刷新失败和不透明请求失败，需要 provider 先给出明确的 retryability 合同。
2. **P1 不应覆盖全部 aborted。** 本轮只确认 1 个用户插话、5 个进程或会话结束，另有 11 个来源不明；没有证据支持把 aborted 统一视为可重试 provider failure。对跨进程恢复的 5 个样本，更合适的是独立的 restore/resume 规则，并继续遵守用户中断、未知写入和不重放工具的边界。
3. **不可重试 error 不应因为用户后来手动“继续”就自动续跑。** 新一轮用户输入可能改变上下文或授权，而自动续跑没有这层新信息。只有错误合同明确为可重试、重试预算已耗尽、且不存在 unknown 写入时，才进入 P1 的有界等待与 continuation。
4. **toolUse 停点不纳入普通 error 自动续跑。** 先只读核验工具状态和结果；能够证明没有派发或没有副作用时，才考虑后续动作。
