### 2.4 用户纠正

- 高摩擦 15 个会话共有 35 个纠正关键词命中。人工阅读后，约 55%–65% 是误报。
- 主要误报来自初始任务书、skill 文本或测试输出本身包含“停止、重新、错误、回滚”等词，不是维护者在纠正 agent。
- 真正的纠正主要有三类：
  1. 修改没有解决真实界面问题，但 agent 已按实现或测试结果认为完成。
  2. agent 扩大了执行范围，或在未确认关键边界时继续实施。
  3. agent 没有把真实外部状态核验完，例如只完成本地改动，却把 PR、发布或真实设备链路当成已完成。
- 这说明关键词可用于粗排，但不能直接当作用户不满率。

### 2.8 工具面

- `search_tools` 调用 27 次，覆盖 22 个会话，0 错误。
- `subagent` 调用 297 次，覆盖 22 个会话，19 次错误；`subagent_wait` 调用 100 次，20 次错误。
- Subagent 是否值得：结论是“取决于验收方式”。用于并行检索、实现和 review 时能提高吞吐；用于替代真实 UI 重放时效果差。`4290f8f2e7` 中多次委派与等待没有解决用户可见问题，而直接复现和验证才是决定性步骤。
- 没有看到模型在真实任务里因“工具不存在或不可见”而失败。文本粗搜到的 6 个命中都来自测试输出，不是实际工具面错误。

### 2.9 Browser / Computer Use

- Browser relay：`browser_inspect` 195 次、23 次错误；`browser_interact` 53 次、7 次错误。
- 结构化错误中 stale/重新 observe 共 3 次，分布在 3 个会话；needs-approval 和 needs-confirmation 都是 0。
- `fe48eeb57f` 中 Browser relay 超时后出现重复 inspect，流程明显卡住；这是本周最清楚的 Browser 失败案例。
- Computer Use 路径使用较少：`find_roots` 17 次但 14 次失败，主要是 validation；`observe_ui` 5 次全成功；`act_ui` 4 次、2 次错误。高 `find_roots` 错误率更像调用合同使用不正确，不是审批卡住。

### 2.10 延迟

- Provider 请求：p50 5.916 秒，p95 45.633 秒；time to first content：p50 2.607 秒，p95 8.633 秒。
- 等待型工具最慢：`subagent_wait` p50 256.086 秒、p95 1800.700 秒；`ask_user_question` p50 342.103 秒、p95 960.264 秒。这些包含子任务或人工等待，不等同于工具执行性能。
- 非等待型工具中，`bash` p50 2.040 秒、p95 88.677 秒；`codemode` p50 2.170 秒、p95 32.896 秒；`browser_inspect` p50 0.304 秒、p95 8.415 秒。
- 因此最值得优化的“执行型慢工具”是长尾 `bash`，其次是 `codemode` 和 Browser inspect；但必须先区分真实长任务与无效重试。

### 2.11 维护者这一周自己的体感

维护者口述：

- 最烦的一件事：停得不对。
- 最常手动纠正的事：执行范围。

## 4. Top 5 改进

### 1. 为长任务增加阶段预算和显式停点
- 问题：单会话持续数小时到数天，范围持续扩张，token 与工具调用失控。
- 证据：`6566172664`、`43b5f93e8f`、`5edfcf424b`；高摩擦第一名有 2987 次工具调用，单会话 token 达到数亿量级。
- 涉及组件：Pi 核心循环与重试、coding-policy、Compaction。
- 粗略建议：按“实现、真实验证、外部交付”分阶段；达到预算或范围变化阈值时自动汇总并重新确认，不默认把新目标并入原会话。

### 2. 让失败后的下一步必须带新证据
- 问题：edit、bash、浏览器和外部状态检查会重复同一路径。
- 证据：305 次重复相同调用；124 次 edit 错误后有 30 次立即再次 edit；`fe48eeb57f` 同一调用最多重复 15 次。
- 涉及组件：内置文件工具、Browser relay、coding-policy。
- 粗略建议：同一失败签名再次调用前，要求先完成 read/observe/状态变化检查；无新证据时强制换路或停止。

### 3. 把真实验收设为 UI 和外部流程的硬门
- 问题：代码和测试通过后，agent 容易过早宣称真实 UI、PR 或发布流程已完成。
- 证据：`4290f8f2e7`、`fe48eeb57f`、`f2448d03b3`。
- 涉及组件：Browser relay、Subagent、coding-policy、Pi 核心循环。
- 粗略建议：UI 必须真实重放；PR review、发布状态和设备结果必须有对应外部证据。证据缺失时只能报告“实现完成，验收未知”。

### 4. 收紧 Subagent wait 与委派验收
- 问题：委派量较大，wait 错误率 20%，且子 agent 结论有时替代了主会话验证。
- 证据：`subagent` 297 次、`subagent_wait` 100 次；`4290f8f2e7` 多次委派后仍需用户指出问题未解决。
- 涉及组件：Subagent、Pi 核心循环。
- 粗略建议：wait 超时后只读检查一次状态；主会话必须对关键结果做独立验证，并限制同一问题的重复委派次数。

### 5. 改善 provider 恢复与状态表达
- 问题：477 次 assistant error 中，connection、fetch failed 和 rate limit 占多数；恢复过程会拉长任务并诱发重复验证。
- 证据：connection 221、fetch failed 83、rate limit 52；重连 9 次，4 个会话最终都恢复。
- 涉及组件：Qoder provider、其他 provider、Pi 核心循环与重试、TUI/footer。
- 粗略建议：明确区分“正在等待网络、请求已失败、结果未知”；恢复后从最近可证明检查点继续，并展示本次恢复是否产生新的 provider 请求。
