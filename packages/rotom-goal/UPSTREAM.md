# Upstream provenance — @narumitw/pi-goal (rotom fork)

This package is a rotom-maintained fork of the third-party Pi extension
`@narumitw/pi-goal`. It is not a Pi fork and not an upstream release.

- Upstream package: `@narumitw/pi-goal`
- Upstream repo: <https://github.com/narumiruna/pi-extensions> (directory `packages/pi-goal`)
- License: MIT (original notice retained in `LICENSE`)
- Fork baseline: **upstream `0.54.4`** source tree (`src/`, 22 TypeScript files), copied byte-for-byte except the changes listed below.
- Fork version: `0.54.4-rotom.0`

## Why 0.54.4 as the baseline

The previously shipped product baseline was `0.52.1`. `0.54.4` was reviewed and
absorbed because it carries improvements worth keeping:

- Token-budget usage is carried by an appended Goal prompt instead of rewriting
  the leading system instructions, so the post-activation provider request
  prefix stays stable (better prompt caching).
- Budget exhaustion stops Goal-owned work immediately instead of queuing an
  extra wrap-up model turn.
- Exhausted transient provider retries enter a quiet active wait instead of
  terminally blocking the goal.
- The three Goal tools register once with stable schemas from startup; the
  `toolVisibility` setting is retired and preserved as unknown data.

## Entry point change vs upstream 0.54.4

Upstream 0.54.4 declares `./dist/index.ts`, a single bundled file generated by
an esbuild script (`scripts/build-runtime.mjs`) that is **not** included in the
published tarball. To keep this fork buildable and reviewable from source
without that missing script, the fork declares `./src/index.ts` as the Pi
extension entry (the same entry style upstream `0.52.1` used). Pi's loader
resolves the `.js` specifiers in `src/` to the `.ts` sources. No `dist/` is
shipped, so there is no risk of a stale bundle diverging from `src/`.

`@narumitw/pi-tui-kit` is a **type-only** import across the entire source
(`import type { ActionMenuItem }` in `src/menu.ts`); it is erased at load time
and never resolved at runtime.

## rotom changes on top of 0.54.4

### `src/safety.ts` — stronger no-progress guard

Upstream only counts a no-progress repeat for runs that make **no** tool call,
and resets the counter whenever any tool is attempted. That lets an agent loop
indefinitely by re-issuing the exact same failing tool call: each attempt resets
the guard, so only the hard automatic-response cap (`automaticTurns`) can stop
it.

The fork replaces the tool-free-only fingerprint with a combined
**text + tool-call-signature** fingerprint (`fingerprintAutomaticRunProgress`,
`toolCallSignature`). A repeat is now counted when an automatic run's observable
behaviour is identical to the previous automatic run — same visible assistant
text **and** same tool names + normalized arguments.

Properties (covered by `test/safety.test.ts`):

- Re-issuing the same failing tool call with the same arguments and the same
  text accumulates toward the existing `noProgressTurns` threshold (default 3)
  and then **pauses** the goal (recoverable via `/goal resume`). It never
  blocks the goal and never auto-retries a write.
- Any genuine progress — different arguments, different text, or switching
  between tool and tool-free output — produces a different fingerprint and
  resets the counter to one, so productive iterative work is never charged.
- When a run makes no tool call, the fingerprint is **byte-identical** to the
  upstream tool-free text fingerprint, so a mid-session upgrade keeps matching
  persisted fingerprints and the persistence normalization stays valid.

This is a behavioural guardrail, not proof of progress. It reuses the existing
`no_progress` pause cause and the existing `noProgressTurns` setting; no new
settings, tools, or persisted state shapes are introduced.

## Not changed

Native code: none (this package is pure TypeScript). Completion
(`goal_complete`) and blocker (`goal_blocked`) semantics are unchanged from
0.54.4: completion evidence and the three-consecutive-turn blocker count remain
model-reported. Strengthening those into independently verified gates would
require an evaluator that reads files/commands, which upstream and comparable
agents also lack; it is intentionally out of scope for this fork to avoid
falsely rejecting valid completions.

## Verification boundary

Verified here (L1): `test/safety.test.ts` via `node --test`. End-to-end runtime
loading is verified by the product loader test in
`rotom/extensions/third-party/index.test.ts`. Real long-running multi-turn
goal behaviour against a live paid model is **not** verified here and needs
explicit authorization.
