## Y2（高，产品）：定向 L2 很可能缺少目标窗口字段

`native/macos/bridge.swift` 的 `postMouseClick` 用 `CGEvent(mouseEventSource: nil, …)` 建事件，只设了位置和
`mouseEventClickState`，**没有设置** `mouseEventWindowUnderMousePointer` 和
`mouseEventWindowUnderMousePointerThatCanHandleThisEvent`。

四次运行里，fixture 窗口都不在前台（`target active` 记录前台是 Scry），点击坐标落在别的窗口上。
目标 App 按窗口号分发事件；没有这两个字段，它不知道这次点击属于哪个窗口，很可能直接丢弃。这能同时解释
“计数没动”和“窗口也没被激活”。这还只是假设，需要实验证实。

修法和实验：

1. 在 `l2` 和 `pid` 两种投递里，给鼠标事件填上目标窗口号（这两个字段都是公开常量），窗口号取自调用方已经解析好的
   `windowId`。`hid` 投递不变。补单元测试或 Swift 自测，确认这两个字段被设置。
2. 冻结前先审核，然后用一次 B0 验证：定向 L2 点击的计数是否从 1 变成 2。

**产品保护（由用户决定）**：从 G4（`145cc21`）起，IntelliJ 在 `background` 策略下默认走 L2，而 L2 在真机上目前是
0 正例、4 负例。建议在 L2 拿到真机正例之前，把它改成需要显式开启（`ROTOM_CU_L2=1` 才走 L2，默认走 `pid`），
并同步修改根 `CLAUDE.md` §4 的说法。这是产品合同的改动，需要用户同意；`pid` 投递在真机上同样还没有正例，
所以这一步只是回到 G4 之前的行为，不代表 `pid` 已经可靠。

## Y3（低）：顺手校准 `pid 0` 的含义

在下一次 B0 里，让 helper 向 HID tap 投一个带 agent 标记、位移为零的 `mouseMoved`（不移动光标），
看它在环形缓冲区里记录成什么 pid 和 state。这样就能知道“经 `CGEventPost` 投递的事件”在这台机器上长什么样。
如果它带的是 helper 的 pid，那么突发的 `pid 0` 就指向更底层的来源；如果也是 `pid 0`，就说明 pid 这条线索不可用。
