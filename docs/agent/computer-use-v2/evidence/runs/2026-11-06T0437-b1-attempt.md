## B1 第一次尝试：fixture 无法启动（脚本缺陷，未执行任何动作）

命令（`--direct-l2`，独立 socket，`PI_CU_L2_SOCKET` 已设，避免脚本自建 socket 并用 `open` 拉起
无权限 helper）：

```
PI_CU_LIVE=1 PI_CU_L2_SOCKET=1 PI_CU_SOCKET_PATH=~/cu-v2-test/direct-l2.sock \
PI_COMPUTER_USE_HELPER_APP_PATH=~/cu-v2-test/pi-computer-use.app ROTOM_CU_BROKER=0 \
node --experimental-strip-types scripts/cu-v2-l2-check.mjs --fixture ~/cu-v2-test/Fixture.app --direct-l2
```

结果（`evidence/runs/2026-11-06T12-51-02-510Z-l2-check.md`）：

| 步骤 | 结果 |
| --- | --- |
| helper diagnostics | pass，protocol=9 accessibility=true |
| environment operator app | pass，Scry pid=45089 |
| fixture fresh copy | pass，bundle=com.example.cu-fixture.1793969462369 |
| fixture 启动 | **fail**：`open -n …` → `-10825` |
| 之后所有动作 | 未执行（脚本 abort） |

根因链：

1. `prepareFixtureRun` 只做 ad-hoc 签名（`codesign --sign -`）。本机 amfid 拒绝 ad-hoc App：
   手动 `open` 该副本得到 `launchd job spawn failed`（NSPOSIXErrorDomain 162）。
2. 改用真实签名身份（Apple Development）后**仍然** `-10825`；进一步确认连原始
   `~/cu-v2-test/Fixture.app` 都无法被 LaunchServices 启动，而它的可执行文件直接运行是正常的
   （pid 47006 起来了）。即旧 fixture bundle 本身在这台机器/这个系统版本上已不可用，
   不是签名问题，也不是路径问题（换到 `~/Applications/` 同样失败）。

## 修复

1. **重建 fixture App**：用仓库里的 `native/macos-fixture/FixtureApp.swift` 重新编译
   （`xcrun swiftc -O -parse-as-library -target arm64-apple-macos14.0 -framework SwiftUI
   -framework AppKit`），配上 `Info.plist`（`CFBundlePackageType=APPL`、`PkgInfo`）、
   Apple Development 签名、bundle id 仍为 `com.example.cu-fixture`。旧 bundle 保留为
   `~/cu-v2-test/Fixture-broken-2026-11-06.app`。重建后 `open -n` 成功（pid 10609）。
2. **`scripts/lib/fixture.mjs` 支持真实签名身份**：新增 `PI_CU_FIXTURE_SIGN_IDENTITY`（未设时保持
   原来的 ad-hoc 行为）。理由是 ad-hoc 在部分机器上根本无法启动，脚本会静默地在第一步失败。
3. 验证脚本实际路径（与脚本相同：复制 → 改 bundle id → 签名）生成的副本，未做 `lsregister` 也能
   `open -n` 成功（probe4/probe5）。控制实验：`prepare` 与 `open`/`pkill` fixture 副本期间
   helper 的真实输入计数**完全不变**（5730 → 5730），说明脚本自己的启动动作不会污染门禁。
