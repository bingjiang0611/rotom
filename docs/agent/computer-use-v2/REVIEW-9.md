规律：**只要 fixture 的窗口出现，就有突发；窗口没出现（不论进程起没起）就没有。**
突发全部是 `pid 0 / state 1`，也就是从 HID 系统状态进来的事件：真实硬件，或者某个虚拟 HID 设备驱动。
App 通过 `CGEventPost` 投递的事件一般会带上投递进程的 pid。
形态是约 125 Hz、持续 0.8 秒的鼠标移动，然后一次按下，像是有东西“看到新窗口出现，就把鼠标移过去点一下”。

## X1（高）：`activates:false` 实验分辨不了激活和窗口出现

`scripts/lib/fixture.mjs:109` 写明：以 `activates:false` 启动的 SwiftUI App 不会建窗口。所以执行方提议的实验里，
“没有激活”和“没有窗口”是同时发生的。突发消失也只能说明二者之一是触发条件，22:14 那次已经给过同样的结果。

要分开两个假设：

- **H-a 激活路径**：`manageApps activates:true` 或 LaunchServices 的激活过程本身产生了这些事件。
- **H-b 外部程序**：机器上有别的程序（自动化工具、远程控制、安全软件、虚拟 HID 驱动）在新窗口出现时驱动鼠标。

设计：让 fixture 可以“出窗口但不激活”。例如加一个启动参数，在 `applicationDidFinishLaunching` 里对主窗口调用
`orderFrontRegardless()`，并且不调用任何 activate。一个窗口里跑三组，每组都是 B0（只出报告），顺序写进授权：

| 组 | 启动方式 | 窗口 | 激活 |
| --- | --- | --- | --- |
| C 基线 | 不启动，空等同样的时长 | 否 | 否 |
| A | `activates:false` 加 `orderFrontRegardless` | 是 | 否 |
| B | 现在的 `activates:true` | 是 | 是 |

判读：A 和 B 都有突发，支持 H-b；只有 B 有，支持 H-a；都没有，说明触发条件还不在这两者里。
每组在启动前和窗口出现后各记一次光标位置（脚本层面已有 `cursorMoved` 的读法，helper 的缓冲区仍然不记坐标），
这样能知道突发有没有真的移动指针。

在 dry run 里用假 backend 覆盖三组的接线；A 组的“出窗口但不激活”只能在真机上验证。

## X2（高，需要用户知道）：用户不在时出现过一次真实点击

第九次窗口里，无人在场的机器上出现了 100 次鼠标移动和一次 `leftMouseDown`（`pid 0 / state 1`），点在哪里不知道。
不管来源是我们的激活路径还是别的程序，这都是在用户桌面上发生的一次点击。B 阶段的结论可以等，这件事不该等。

在下一个窗口之前，执行方可以先做**只读**检查（不启动、不操作任何 App）：

- `hidutil list` 和 `ioreg -r -c IOHIDUserDevice -l`：列出虚拟 HID 设备，以及创建它们的进程或驱动。
- 列出拥有“辅助功能”或“输入监控”权限、并且正在运行的程序（只读 TCC 状态，或者请用户在系统设置里看）。

另外，有两个问题只有用户能回答：

1. **Scry 和 Etch 是什么程序？** 它们反复出现在前台。第三次窗口（2026-11-06 23:03–23:19）里前台在 Scry、Chrome、Etch
   之间切换，同时有 39,540 个未标记事件。那段时间用户在不在机器前？这个问题第 7 轮问过，还没有回答。
2. 机器上有没有装远程控制、键鼠共享、自动化或“防休眠”类软件？
