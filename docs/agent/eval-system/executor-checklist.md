# 执行者推送前自查清单

每个任务推送前逐条过一遍，并在报告末尾写「自查」一节：每条写「做了 / 不适用」，附上命令和结果。目的是把核验时常见的返工问题提前在自己这边发现。任务 14 来回了 4 轮，多数问题都出在下面这些点上。

## 1. 测试与审计

- [ ] 跑受影响的测试。eval 侧跑 CI 里同一串 `npm test -- …`；dashboard 侧跑 `node --test …`。typecheck 要通过。
- [ ] `python3 scripts/audit-public.py --root .` 结果为 PASS。报告和核验文字里**不要**写像真密钥的字面量，用文字描述代替。
- [ ] `git diff --check` 干净，只推 `eval/system`，使用 noreply 身份。

## 2. 判定（规则、正则、打分函数）

每改一个判定，都要用下面三类样例各试一遍，并把样例加进对照测试：

- [ ] **合理但写法不同的答案**会通过：中文和英文、换一种说法、用 `for` 循环或 `grep` 代替直接命令、「停下来问用户」这类正当的另一种做法。
- [ ] **接近合格的坏答案**会失败：空泛回复（如「预算用完了」）、谎报数量、只说完成不说剩余、遇到失败就把问题原样推回给用户。
- [ ] **数量或状态要对得上实际。** 凡是判定读回复里的数字或状态，都要拿工作区文件或日志核对，不能只看措辞。

正则补了一个词之后，回头检查是否把明显不合格的回复也放了过去。

## 3. 用例与 fixture

- [ ] prompt 是用户真会说的话：不提示正确做法，不出现判定用的词，也没有「用户已授权」之类会让错误变得合理的说法。
- [ ] 工作区文件里不出现 `synthetic`、`fixture`、`stub`、`eval`、`test`、「桩」「测试」，也不写设计意图。`--help`、注释要和实际行为一致。
- [ ] 任务确实做得下去：需要的文件名、工具、权限都具备。用一次「理想 agent」的手工推演确认能走通。
- [ ] 想测的场景真的会发生，比如「做了一半被打断」，不会退化成别的情况。

## 4. 计数与汇总

- [ ] 会被多次调用的函数（二分搜索、重试、重新渲染）不能重复累加计数。用同一份输入跑两遍，结果必须相同。
- [ ] `String.replace` 回调的参数个数取决于正则有几个捕获组。没有捕获组的规则不能按有捕获组的方式读参数。
- [ ] `unknown` 单独计，不能算成通过，也不能算成失败。

## 5. 脱敏与隐私

- [ ] 改了脱敏规则，就同时试两组样例：**必须脱敏**的（小写十六进制 `sk-`、`OPENAI_API_KEY=…`、JSON 里 `"apiKey": …`、纯数字密码、同一段文本里出现两三种不同的 key），以及**不能误伤**的（`PWD=/…`、`os.environ[…]`、`max_tokens`、`sk-learn-…`、git SHA、UUID）。
- [ ] 真实会话原文、卡片、标注、回放输出只放 `~/.rotom/evals/`，权限 0700/0600，不进仓库、报告和聊天。报告里引用片段时，先把路径、用户名、主机名替换掉，每段不超过 200 字。
- [ ] 不在真实会话上触发 judge 或回放，除非任务说明明确授权。

## 6. 真实模型运行

- [ ] 遵守任务给的次数上限，不补跑；`unknown` 超过阈值就停。
- [ ] 两臂的 SHA 用 Git 读取，第三方依赖按 CI 参数安装（`--legacy-peer-deps`）。
- [ ] 每一条没通过的检查都要复核，归为「真实行为问题」或「判定误判 / 题目问题」，并写理由。判为真实问题之前，先排除题目歧义，比如用户已经知情并拍板的情况。

## 7. 报告

- [ ] 写清改动、命令和结果、未验证项（L1/L2/L3 分开写），以及与任务说明的偏差。
- [ ] README 状态表对应那一行改成 `in-review`。
