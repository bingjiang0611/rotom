# 连续压缩失败的溯源（2026-11-25）

只读排查：不调模型、不改产品代码。回答两个问题：压缩为什么失败，失败为什么不停。

## 结论

- 两台机器各跑过一次 harvest：一台 0 次，另一台 135 次、9 个会话。本文只覆盖出问题的这台。
- 127 次（94%）落在同一个摘要模型 **S1** 上（窗口 131 072、输出上限 8 192、anthropic-messages 协议的公司网关）；另外 8 次是别的模型的可归类错误（http 3、provider_error 4、timeout 1）。
- 形态固定：摘要请求发出后 **40–55 s（中位 48 s）内没拿到响应头，也没有任何 thinking/text 事件**，连接随后报错；错误文本匹配不上任何分类规则，落到 `unknown`。
- 不是上下文超限：失败与成功的 `tokens_before` 大幅重叠，同一模型另有 26 次成功摘要。不是供应商宕机：失败簇内同模型普通请求照常成功。
- 连续重试是产品行为：一次失败只发事件、返回 `false`，不改上下文、不记次数、不设冷却；下一条 assistant 消息后 `_checkCompaction` 用同一条旧 usage 又判定超阈值，2–10 s 再打一次，没有退避。
- 上一份梳理里「压缩失败由摘要不可解析触发」的推断不成立：没有任何一次摘要请求返回过内容（§4.1）。

## 0. 方法与脱敏

- 数据源：本机 `~/.rotom/loop/` 最新 harvest 目录（`incidents.jsonl` 计数）与各会话 `observability/<session>.trace.jsonl`（span 时序）。会话 JSONL 只用于确认「没有落盘的错误文本」。
- 会话记作 A / B / C，模型记作 S1 与 M1–M5（真实 id 是本机基础设施标识，不进仓库）；不含 session id、主机名、路径、项目名、供应商 URL。
- 证据等级：状态、耗时、`tokens_before`、span 结构是实测；「网关缓冲 / 上游超时 / 缓存未命中」是推断，逐条标注；错误原文拿不到（§5.3）。

## 3. 跨会话归纳

### 3.1 集中在同一个摘要模型

167 次尝试里 149 次用 S1，18 次用另外四个模型（M1 4、M2 7、M4 4、M5 3），而这 18 次**一次没失败**。S1 自己也不是全挂：26 次成功。所以是「某个 provider/模型 + 摘要请求形态」的组合问题，不是压缩逻辑普遍坏掉。放大到本机 9 个失败会话（135 次）结论一样：S1 127 次，余下 8 次是可归类错误。

### 3.2 不是上下文超限

| 会话 | 成功 tokens_before | 失败 tokens_before |
|---|---|---|
| A | 103 973 – 248 731 | 104 000 – 170 247 |
| B | 105 318 – 245 308 | 96 683 – 127 297 |
| C | 120 844 – 236 039 | 105 104 – 127 015 |

区间大幅重叠：A 里 104 k 会失败、119 k 会成功。交叉验证：本机 `compaction.reserveTokens = 27200`，131 072 − 27 200 = 103 872 正好是 A 失败区间下沿，272 000 − 27 200 = 244 800 正好是最大几次成功的量级——**触发阈值本身正常**，问题发生在阈值之后的摘要请求上。

### 3.3 不是供应商宕机

A 最长那簇（02:34–02:46，12 次连续失败）窗口内，同模型普通流式请求成功 11 次；B 的 33 次长簇里 32 次、C 的 24 次长簇里 21 次。普通请求能过、摘要请求过不去，问题在请求形态。

### 3.4 失败形状：无响应头、无内容

| 指标 | 失败 (123) | 成功 (S1, 26) |
|---|---|---|
| 耗时 | 40–55 s，中位 48 s | 23–53 s，中位 41 s |
| `first_thinking_ms` / `first_text_ms` | 全缺 | 26/26 有 |
| 有无 `pi.ai.prefill` 子 span | 0 / 149 | 有 |

- `pi.ai.startup` 的语义是「请求发出 → 收到响应头或首个内容事件」。失败案例里它挂到 40–55 s 后以 `error` 结束，期间既没 `providerResponse`（收响应头）也没 `messageUpdate`（首个内容）。
- `pi.ai.prefill` 是「响应头 → 首个内容」，由 `providerResponse()` 创建。**没有任何一次压缩请求产生过 prefill span**；对照 S1 的 1115 次普通请求里 1111 次有（99.6%）。所以「没收到响应头」不是记录盲区——该模型平时能记，压缩时没记。
- 也不是固定客户端超时：成功压缩最长 53 s，失败跨 40–55 s，本机 HTTP idle 超时默认 300 s，产品侧没有 48 s 附近的超时。

### 3.5 重试节奏：没有退避，也没有失败记忆

相邻尝试间隔 2–10 s，中间只夹一两条普通请求，就是一次 assistant 回合。失败簇没有放弃信号：B 连打 33 次（47.6 min）、C 连打 24 次（26.9 min）。失败率不是 100%：A 的 9 个簇最后都靠一次成功收尾——同一条请求打到第 N 次会成功，产品等不到「这次不行就停」。

### 3.6 收场

A 最后一次压缩成功后继续跑了 980 次请求，会话正常。B 最后一次 overflow 恢复失败后还有 29 次成功请求，然后结束。C 最后一次 overflow 失败后**一次请求都没有**，会话直接终止——上下文已溢出、压缩又失败，这一次最糟。B、C 各有 2–4 次 `overflow` 触发且 `will_retry=false`：溢出恢复本来就关了重试，失败之后仍会在下一条消息上重新触发，于是形成长簇。

## 4. 代码路径

### 4.1 一次失败走过的路径

| 阶段 | 位置 | 行为 |
|---|---|---|
| 触发判定 | `packages/rotom-pi/packages/coding-agent/src/core/agent-session.ts:3198` `_checkCompaction()` | 用最近一条 assistant 的 usage 比 `contextWindow - reserveTokens` |
| 阈值 / 溢出分支 | 同上 `:3329` / `:3263` | `_runAutoCompaction("threshold" \| "overflow", false)` |
| 组装 preparation | `:3344` `_runAutoCompaction()` | 切点、`tokensBefore`、是否 split-turn |
| 摘要调用 | `:2952` `_runDefaultCompaction()` | 取模型/鉴权/thinking 级别，传 `getRetrySettings()` |
| 摘要实现 | `src/core/compaction/compaction.ts:1029` `compact()` | split-turn 时并行两个摘要请求（`:1058`），任一失败 abort 兄弟 |
| 单次请求 | 同文件 `:663` `completeTimedSummarization()` | `cacheRetention: "none"`（`:675`）、`retryAssistantCall`（`:698`） |
| 失败返回 | `agent-session.ts:3462` catch | 发 `compaction_end`（`willRetry:false`）、`_emitSessionCompactFailed`（`:3479`）、`return false`（`:3487`） |

与实测一致：失败的压缩 span 下只有 1 个 `pi.ai.request` 和 1 个 `pi.ai.startup` 子 span——一次压缩 = 一次请求，没有内部重试。

### 4.2 为什么失败不停止

catch 只做三件事：发 `compaction_end`、发 `session_compact_failed`、返回 `false`。**不改上下文、不记失败次数、不设冷却、不换模型**。而 `_checkCompaction` 的依据是「最近一条 assistant 的 usage」，失败压缩没改历史，判定条件依然成立，下一条消息后立刻再打一次——这就是 2–10 s 间隔和 33 次长簇的来源。

`_emitSessionCompactFailed`（`agent-session.ts:1149`）只发扩展事件，不写 session entry。实测对照：三个会话的 JSONL 搜不到 `Auto-compaction failed` / `Summarization failed` / `session_compact_failed`（命中 0）。失败既不落盘也不计数。

### 4.3 为什么没有内部重试

`getRetrySettings()` 返回默认 `enabled:true`、`maxRetries:3`、`baseDelayMs:2000`（`settings-defaults.ts:18`；本机没覆盖 `retry`）。但实测每次失败只有 1 个请求 span，说明 `retryAssistantCall`（`packages/rotom-pi/packages/ai/src/utils/retry.ts:244`）没进重试分支。

原因在 `isRetryableAssistantError`（同文件 `:313`）：只有错误文本匹配「可重试」正则表才重试；匹配不上立刻返回。这条文本既没匹配可重试表，也没匹配配额表，于是**被当成确定性错误、一次就放弃**。同一「匹配不上」在观测侧就是 `pi.ai.error.category = "unknown"`（`rotom/extensions/observability/model-metadata.ts:27`，注释写明「不猜」）。两套独立正则，对这条文本结论一致：不认识。

### 4.4 排除 split-turn 并行

`compact()` 在 split-turn 时并行发两个摘要请求（`compaction.ts:1058`）。实测排除「并行打挂网关」：123 次失败里 101 次是单请求（`request_starts=1`），22 次并行；成功里也有 16 次并行。

## 5. 实测 / 推断 / 未验证

### 5.1 实测（可复核）

- 135 次 `compaction_failed`：9 个会话、一台机器；S1 127 次，其余 8 次可归类。
- 三个重点会话 167 次尝试：失败 123 次全在 S1，`threshold` 117 / `overflow` 6，耗时 40–55 s（中位 48 s）。
- 123 次失败全部 `category=unknown`、`will_retry=false`、无 `first_thinking_ms`/`first_text_ms`、无 `pi.ai.prefill` 子 span。
- 失败簇内同模型普通请求照常成功：A 42 次、B 38 次、C 28 次；S1 的 1115 次普通请求里 1111 次记了响应头。
- 相邻尝试间隔 2–10 s；长簇 33 次 / 47.6 min、24 次 / 26.9 min。
- 版本：A `0.1.27-main.50ccdc87` / `1.4.0-rotom.2`；B、C `0.1.27` / `1.4.0-rotom.4`。本机 `reserveTokens = 27200` 与 103 872 阈值吻合。

### 5.2 推断（未证实）

- **上游/网关在响应前就断了**。实测只证明「没响应头、没内容、48 s 后报错」，不证明谁先断：可能是网关排队超时、上游拒收、或中间设备重置。
- **缓存未命中放大耗时**。代码里摘要请求固定 `cacheRetention:"none"`（`compaction.ts:675`）。普通请求命中 prompt cache 时 prefill 中位 435 ms；摘要是一次十几万 token 的未缓存预填充，理论上要几十秒，若网关对首字节有上限，正好落在 40–55 s。**机制上说得通，但没有直接证据**（拿不到网关日志，也没有缓存命中率对照）。
- **错误文本像一段非标准网关话术**（不含状态码、也不含 timeout/network 关键词），所以两套正则都不认。没有原文，无法确认。
- **间歇性失败、打到一定次数自己好**，更像限流/容量，不是配置错误。

### 5.3 无法验证

- **错误原文拿不到**：`compaction_end` 里带着 `Auto-compaction failed: <原文>`，但只走扩展事件；observability 按合同只记分类、不记正文；本机没有 `~/.pi/agent/logs`，会话 JSONL 里也没有。要拿原文得临时开诊断日志，属于改产品行为，本轮不做。
- **网关侧无日志**：本机 `~/Library/Logs` 下没有该网关客户端日志，上游响应内容不可见。
- **trace 缺 `rotom.build.commit`**：只能定到版本，读不到 commit。
- **没有对照实验**：要证明「换模型就不连续失败」，得在同一会话上换摘要模型重跑，属于改产品配置，未做。
- 另一台机器 `compaction_failed` 为 0，只能说不曾发生，不能推断它的 provider 更稳。

## 6. 对回归用例的意义

- 不适合做续跑类确定性用例：根因在外部网关的首字节行为，本地 harness 无法稳定复现「48 s 无响应头」，mock 出来的只是我们自己的假设。
- 但 §4.2 是产品逻辑，且可复现：**压缩失败后不记状态、不冷却，下一条消息立刻重试**，长簇可以无限延续。用例切入点应是「一次压缩失败之后应当发生什么」，而不是「网关为什么失败」。
- 具体形态留给下一步设计，本文不改代码。
