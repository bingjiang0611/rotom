# rotom 0.2.0 发布说明（草稿，目标 dist-tag：latest）

## 升级前必读：必须显式更新 Computer Use helper

> **本版计划发布到 `latest`。旧 helper 与本版协议不兼容：不完成下面的 helper 更新，Computer Use 会报协议不匹配，不能正常使用。仅升级 rotom 或重开旧 helper 不够。**
>
> 本文是草稿，不表示已经发布。用户已明确授权 `0.2.0` / `latest`；当前产品 manifest 仍为 `0.1.27`。须先将功能合入 main，再单独提交并冻结发布元数据，之后才构建、验证最终产品 tgz。当前候选不执行发布或切换日常安装。

安装最终 rotom 版本后，按以下顺序操作：

1. **退出所有使用该 helper 的 rotom 会话。** 保存工作，不要只关闭授权弹层。
2. **退出旧 helper。** 它是独立进程；关闭终端不一定退出 helper。更新期间保持会话和旧 helper 关闭，不让其他进程重新启动它。
3. **受管 Mac：先设置已有且获准使用的签名身份。** 例如在自己的终端设置：
   ```sh
   export PI_COMPUTER_USE_CODESIGN_IDENTITY='<已有、获准的签名身份>'
   ```
   没有合适身份或系统拒绝签名时，停止并联系管理员。不要创建临时证书、导出私钥、关闭安全软件或重置系统权限来绕过策略。
4. **由用户显式运行更新命令：**
   ```sh
   rotom helper update
   ```
   它安装到 `~/Applications/pi-computer-use.app`，保持 bundle id `com.injaneity.pi-computer-use`，只签署安装副本。发现目标被进程占用或无法确认占用状态时会拒绝；不会杀进程、启动 helper 或重启会话。只有命令明确成功才进入下一步；失败或结果未知时先检查报告路径，不盲目重跑。
5. **再开新会话**，检查 Computer Use 的协议和权限。自定义 helper 路径/socket 不会自动迁移；新会话应选择本次更新的路径，或者由用户另行维护那个独立安装。

未设置签名身份时，更新器保留归档签名，**不会自动生成本地证书**。发行归档的 macOS helper 为 ad-hoc 签名，覆盖已有 helper 默认仍会被保护规则拒绝。只有系统策略允许、且用户明确接受 ad-hoc 替换时，才可自行设置 `PI_COMPUTER_USE_ALLOW_ADHOC_UPDATE=1` 后更新；这不是受管 Mac 策略的替代方案，也不保证程序能启动。

### 屏幕录制的系统确认

ScreenCaptureKit 的屏幕录制授权可能按 macOS 的系统策略出现**每月一次的确认弹窗**，具体取决于系统版本与管理策略。用户须自行处理该系统弹窗。它不同于 rotom 的 App 授权卡；rotom 不会自动确认、绕过或把拒绝当作成功。未确认时，屏幕观察或截图可能不可用。

## 新增能力与协议变化

以下是代码与接口的变化，不是未经限定的真机成功声明。helper 协议为 **11**，broker 协议为 **2**；证据分级见下一节。

- 原生 `AXOpen` 路径支持打开目标；文件/App 的外部打开需要单独确认，并在派发前核验目标没有变化。
- Computer Use 授权使用 Ask 的实际问卷与弹层，等待完整授权期限。超时、拒绝和取消不会被当成授权，也不会触发模型续跑。
- 新增 `rotom helper update`。首参 `helper` 由 rotom launcher 处理，不透传 Pi，不启动 AgentSession。
- 两个 macOS 构建入口共用完整 Swift 源文件列表；测试前恢复完整 TypeScript 检查，不再用过渡性的 fatal-only 检查代替它。
- 组件候选为 `@injaneity/pi-computer-use@0.5.1-rotom.4`，取代 main 的 `.rotom.3`。保留 main 的显式重启确认、错误提示和协议回归修复；重启确认不会安装新二进制，不能代替上述升级步骤。

## 行为变化摘要

下列十项对应 [详细行为变化](../agent/computer-use-v2/behaviour-changes.md)；不能把实现合同当作真实环境的隔离保证。

1. **首次向 App 写入需要授权。** 按 App 身份分为 `view`、`click`、`full`；项目配置只能收紧，不能扩大用户全局授权。
2. **无人能展示授权时，未授权写入失败。** 返回 `approval_unavailable`，不悄悄降级。已有有效授权与无授权是两种情况。
3. **跨 agent 的 App 写入由 broker 仲裁。** 冲突返回 `resource_busy`；只有显式请求等待才进入有界队列。
4. **剪贴板也受共享租约约束。** 恢复前检查租约和当前内容，无法安全恢复时放弃，不覆盖用户后来复制的内容。
5. **强制退出单独确认。** 已获得 App 的 `full` 授权，不等于可以省去强制退出确认。
6. **普通 agent 的打扰暂停不能由模型自行解除。** 观察到动作切换前台且用户近期有真实输入时暂停该 agent、撤销租约；恢复由用户发起。
7. **helper 校验租约 token、有效期、目标和撤销状态。** 目前仅有 L1 证据；helper 角色仍是自报，仲裁依然按协作式边界描述，不是同一用户下任意进程的安全隔离。
8. **前台接管是额外许可。** 在许可范围内，真实输入会使接管暂停；只有安静期和原窗口、授权、租约仍有效才可有界恢复。停止/超限会硬结束；中断文本不续打，旧动作不重放。这与第 6 项的普通 agent 暂停不同，且尚无真机通过记录。
9. **IntelliJ 后台点击默认使用 L2。** 用户决定保持开启，但真机结果是 **0 次成功、5 次失败**，可能没有效果；不能承诺 pid 投递可解决它。
10. **输入法分流（H2）。** 输入法启用且目标可写时，`typeText` 优先 AX 插入；普通键盘布局保持原按键路径。写入已被接受但读回未知时不重发按键。本项只有离线证据。

## 已知限制与证据等级

下面原样保留 HANDOFF-6 的证据表。用户报告属于用户报告；没有留存细节的部分不补写为完整可复现记录。历史版本的实测不等于本候选或最终 npm tgz 的新验收。

| 能力 | 证据层级 |
| --- | --- |
| Finder 后台读取、AXOpen 打开文件夹、Ask 授权弹层、授权等待不再提前放弃 | 真机，用户报告不打扰（REVIEW-18、20、22） |
| 打开文件或 App 的确认（O1） | 真机通过（用户报告，细节未留存） |
| L2 定向投递 | 真机 0 次成功、5 次失败；IntelliJ 后台点击默认走 L2（用户决定保持开启），可能不生效 |
| pid 投递 | 真机没有成功记录 |
| 后台打字、输入法分流（H2）、剪贴板恢复、前台接管暂停与恢复、租约强制校验 | 只有离线测试和原生自测（L1） |
| B 阶段 B1–B6 | 未通过；本机端点安全会终止每次换新 bundle id 的 fixture 副本 |

此外：

- Computer Use 使用本机用户权限。同意层、App 分级、租约和暂停机制不是 OS 沙箱。
- updater 的目录锁只串行化 updater，不能阻止旧 launcher 或外部进程在最后占用检查之后启动 helper。整个更新期间必须保持所属会话关闭。
- 签名严格校验通过不等于公证、企业策略批准或实际启动成功。日常 helper、用户证书和真实升级本轮均未操作。
- 最终 `0.2.0` 产品 tgz 发布前，仍须在独立 HOME/prefix 验证实际 helper 启动和 diagnostics；受管 Mac 阻止启动时必须停止发布，不能拿离线测试替代。
- 本候选只等待审核，不推 main；之后须另行完成合入、发布元数据冻结、最终 artifact 验证和用户前台 npm 发布交接。
