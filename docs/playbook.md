# rotom Playbook

rotom 不是“Pi + 一组扩展”，而是一套对 agent 执行方式有明确约束的个人 coding agent。Pi 提供通用机制，rotom 负责给出经过维护的默认行为。

## 核心特性

### 1. 结果必须有证据

rotom 区分“操作已派发”和“目标已完成”：证据不足就返回 `unknown`，不会重放可能已经发生的写操作；浏览器、桌面和子任务也会验证当前状态。**好处是避免点错位置、重复输入或启动重复任务，同时减少纠错和重复执行浪费的 token 与等待时间。**

### 2. 编码过程有固定规则

执行命令或修改文件前，rotom 会先确认仓库、路径、脚本和编辑位置；超时或编辑失败后先读取当前状态，再给出修复提示。**好处是减少改错仓库、无效命令和长任务重跑，既保护用户现有工作，也减少返工消耗的 token 和开发时间。**

### 3. 工具按需加载

rotom 默认只保留常用工具，Subagent 等专用能力需要时再通过 `search_tools` 加入，并随会话恢复。**好处是每轮少发送无关 schema，为代码和任务信息留出更多上下文，并减少无效 token 与工具误调用。**

### 4. 新增本地可观测性

rotom 新增了本地 trace 和 dashboard，把会话、模型请求、工具调用及上下文压缩串成可查询的执行链。**好处是能直接看出慢在哪里、失败在哪一层和用了多少资源，减少反复试错与排障时间，同时不保存 prompt、模型输出或工具正文。**

## 为什么不是直接使用 Pi

Pi 允许用户自行实现这些策略，但也把重试、工具面、日志和恢复规则的设计与维护责任交给用户。rotom 将它们做成统一默认值：有证据才承诺、先确认再修改、按需提供工具，并内置完整的本地执行观测。

如果你想自行组装 agent，直接使用 Pi 更合适；如果你希望安装后直接获得这套一致行为，应使用 rotom。

## 开放源码基础的价值

开放源码让 rotom 可以在问题所属层修复、审计真实行为，并在验证后吸收上游更新，而不是把所有问题堆进 prompt。它不自动等于安全：工具仍以本机用户权限运行，rotom 根产品目前为 `UNLICENSED`。
